**▌ ۱. اصول پایه معماری**

**•** معماری فرانت‌اند به‌صورت Feature / Module Based طراحی می‌شود؛ هر Domain اصلی سیستم یک ماژول مستقل خواهد داشت.

**•** کد مربوط به یک Domain تا جای ممکن داخل همان ماژول باقی می‌ماند و فقط موارد واقعاً عمومی وارد shared می‌شوند.

**•** Page محل انباشته‌کردن منطق نیست؛ Page عمدتاً نقش Composition و چیدمان اجزای صفحه را دارد.

**•** ارتباط HTTP، منطق Domain، منطق React و UI از یکدیگر تفکیک می‌شوند.

**•** ساختار باید برای رشد فازهای بعدی RWMS مناسب باشد و افزودن ماژول جدید باعث آشفتگی پوشه‌های موجود نشود.

**•** از ایجاد پوشه‌ها، abstractionها و لایه‌های بدون نیاز واقعی خودداری می‌شود؛ معماری باید تمیز باشد، نه نمایشی.

|     | **اصل کلیدی**<br><br>Shared سطل زباله پروژه نیست. هر چیزی که فقط متعلق به Item، Waybill، Warehouse یا هر Domain دیگر است باید در همان Module بماند، حتی اگر بیش از یک Component از آن استفاده کند. |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

**▌ ۲. ساختار سطح اول پروژه**

```
src/
├── app/
├── modules/
└── shared/
```

| **بخش**     | **مسئولیت**                         | **قاعده معماری**                                                                                  |
| ----------- | ----------------------------------- | ------------------------------------------------------------------------------------------------- |
| **app**     | راه‌اندازی و هماهنگی کل Application | موارد سراسری مانند Router، Providerها، Layoutها و Configهای Application در این بخش قرار می‌گیرند. |
| **modules** | Domainها و Featureهای کسب‌وکار      | هر Feature اصلی RWMS یک مرز مستقل دارد و کدهای مربوط به خودش را نگه می‌دارد.                      |
| **shared**  | ابزارها و اجزای واقعاً عمومی        | فقط موارد مستقل از Domain و قابل استفاده در چند ماژول در این بخش قرار می‌گیرند.                   |

**▌ ۳. ساختار استاندارد هر Module**

```
modules/
└── <feature>/
    ├── api/
    ├── components/
    ├── hooks/
    ├── pages/
    ├── services/
    ├── schemas/
    ├── types/
    ├── utils/
    └── index.ts
```

**نکته: وجود همه این پوشه‌ها در هر ماژول اجباری نیست. هر پوشه فقط زمانی ایجاد می‌شود که نیاز واقعی وجود داشته باشد.**

**▌ ۴. مسئولیت اجزای داخلی Module**

| **بخش**        | **مسئولیت**                     | **قاعده معماری**                                                                                                |
| -------------- | ------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| **pages**      | صفحات قابل Route شدن            | صفحه‌ها اجزای Feature را کنار هم می‌چینند و نباید به محل منطق سنگین تبدیل شوند.                                 |
| **components** | UI اختصاصی همان Domain          | Componentهایی که مفهوم Domain را می‌شناسند داخل همان Module می‌مانند؛ مانند ItemForm یا WaybillTable.           |
| **api**        | ارتباط با Backend               | توابع HTTP مانند دریافت، ثبت، ویرایش و حذف. Business Logic در این بخش قرار نمی‌گیرد.                            |
| **services**   | منطق مستقل Feature / Domain     | عملیات منطقی و قابل تست که به React یا جزئیات HTTP وابسته نیستند.                                               |
| **hooks**      | منطق وابسته به React            | اتصال داده، State و رفتارهای Feature به Componentها در قالب Hookهای React.                                      |
| **schemas**    | قواعد اعتبارسنجی داده و فرم     | تعریف معتبر بودن داده؛ با TypeScript Type تفاوت دارد و در آینده می‌تواند با ابزارهایی مانند Zod پیاده‌سازی شود. |
| **types**      | مدل‌های TypeScript همان Feature | Type و Interfaceهای اختصاصی Domain مانند Item، CreateItemRequest و DynamicField.                                |
| **utils**      | توابع کوچک و Pure مختص Feature  | Utilityهایی که Domain-specific هستند و نباید بدون دلیل به shared منتقل شوند.                                    |
| **index.ts**   | Public API ماژول                | مرز خروجی Module برای importهای بیرونی؛ بدون تبدیل‌کردن پروژه به شبکه‌ای از Barrel Fileهای غیرضروری.            |

**▌ ۵. جهت مسئولیت و جریان معمول**

```
Page
  ↓
Components
  ↓
Hooks
  ↓
Services
  ↓
API
```

این نمودار یک زنجیره اجباری برای همه سناریوها نیست؛ هدف آن تفکیک مسئولیت‌هاست. Component ساده می‌تواند مستقیماً از Hook استفاده کند و Service فقط زمانی ایجاد می‌شود که منطق Domain واقعی وجود داشته باشد.

**▌ ۶. تفاوت API و Service**

| **بخش**     | **مسئولیت**                        | **قاعده معماری**                                                                  |
| ----------- | ---------------------------------- | --------------------------------------------------------------------------------- |
| **API**     | چطور با Backend صحبت کنیم؟         | Endpoint، Method، ارسال Request، دریافت Response و جزئیات HTTP.                   |
| **Service** | با داده چه منطق مستقلی انجام دهیم؟ | Merge، Normalize، محاسبه، تبدیل یا قواعد Domain که نباید به HTTP یا UI گره بخورد. |

|     | **نمونه مفهومی**<br><br>اگر چند Category فیلد داینامیک داشته باشند و لازم باشد فیلدهای تکراری Merge یا Normalized شوند، دریافت داده وظیفه api است اما منطق Merge می‌تواند در service همان Feature قرار بگیرد. |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

**▌ ۷. تفاوت Type و Schema**

| **بخش**    | **مسئولیت**           | **قاعده معماری**                                                         |
| ---------- | --------------------- | ------------------------------------------------------------------------ |
| **Type**   | شکل داده چیست؟        | مثلاً name یک string و price یک number است.                              |
| **Schema** | چه داده‌ای معتبر است؟ | مثلاً name اجباری است، code حداقل طول مشخص دارد و price نباید منفی باشد. |

در RWMS این تفکیک به‌ویژه برای فرم‌های داینامیک مهم است، چون بخشی از قوانین فرم بر اساس فیلدهایی خواهد بود که از Backend دریافت می‌شوند.

**▌ ۸. قرارداد Shared**

**نمونه موارد مناسب برای shared:**

**•** Button، Input، Select، Modal، Badge، DataTable و اجزای عمومی Design System

**•** PageHeader، EmptyState، LoadingState و اجزای مستقل از Domain

**•** API client عمومی، Hookهای واقعاً سراسری، Utility و Typeهای عمومی

**نمونه موارد نامناسب برای shared:**

**•** ItemTable، ItemCategorySelector، WaybillForm و هر Componentی که یک Domain مشخص را می‌شناسد

**•** منطق Business مختص یک Feature

**•** Typeهایی که فقط در یک Module مصرف می‌شوند

**▌ ۹. قرارداد App**

```
app/
├── config/
├── layouts/
├── providers/
└── router/
```

این ساختار نشان‌دهنده مسئولیت‌های سراسری Application است. جزئیات دقیق Router، Providerها و کتابخانه‌های مرتبط در نسخه‌های بعدی معماری و پس از تصمیم‌گیری فنی نهایی تثبیت خواهد شد.

**▌ ۱۰. نمونه Module کالا**

```
modules/items/
├── api/
│   └── item.api.ts
├── components/
│   ├── ItemForm.tsx
│   └── ItemTable.tsx
├── hooks/
│   └── useItems.ts
├── pages/
│   ├── ItemListPage.tsx
│   ├── ItemCreatePage.tsx
│   └── ItemEditPage.tsx
├── services/
│   └── item.service.ts
├── schemas/
│   └── item.schema.ts
├── types/
│   └── item.types.ts
├── utils/
│   └── item.utils.ts
└── index.ts
```

**این مثال الگوی مفهومی است، نه دستور ایجاد همه فایل‌ها از روز اول. ساختار واقعی هر Module باید فقط به اندازه نیاز همان Feature رشد کند.**

**▌ ۱۱. قواعد نام‌گذاری و مرزبندی اولیه**

**•** نام Moduleها بر اساس Domain کسب‌وکار انتخاب شود؛ مانند items، categories، waybills، warehouses، requests و auth.

**•** Componentهای React با PascalCase نام‌گذاری شوند؛ مانند ItemForm.tsx و ItemListPage.tsx.

**•** فایل‌های api، service، schema و types با نام Feature مشخص شوند؛ مانند item.api.ts و item.service.ts.

**•** کد Domain-specific بدون دلیل در ریشه src یا shared قرار نگیرد.

**•** وابستگی بین Moduleها باید حداقل و کنترل‌شده باشد؛ استفاده بیرونی ترجیحاً از Public API ماژول انجام شود.

**•** هیچ Page یا Componentی نباید به دلیل رشد Feature به فایل چندصد/چندهزارخطی تبدیل شود؛ در صورت رشد، مسئولیت‌ها تفکیک می‌شوند.

**▌ ۱۲. فناوری‌ها و تصمیم‌های تثبیت‌شده در V1**

| **بخش**                        | **مسئولیت**             | **قاعده معماری**                                                                           |
| ------------------------------ | ----------------------- | ------------------------------------------------------------------------------------------ |
| **React**                      | فریم‌ورک UI             | مبنای پیاده‌سازی فرانت‌اند.                                                                |
| **TypeScript**                 | زبان توسعه              | برای Type Safety و نگهداری بهتر پروژه بزرگ.                                                |
| **Vite**                       | Build Tool / Dev Server | اسکلت اولیه پروژه با Vite ایجاد شده است.                                                   |
| **Tailwind CSS**               | Styling                 | پایه Styling و پیاده‌سازی Design System؛ رنگ‌ها و ظاهر بر اساس قرارداد تم RWMS خواهند بود. |
| **Feature-based Architecture** | ساختار اصلی             | مرزبندی پروژه بر اساس Domain/Module.                                                       |

**▌ ۱۳. تصمیم‌هایی که در V1 عمداً نهایی نشده‌اند**

**•** Router و ساختار نهایی Route Guardها

**•** State Management سراسری و Server State

**•** کتابخانه Form Management

**•** کتابخانه Validation؛ Zod یکی از گزینه‌های جدی است اما هنوز قرارداد نهایی نیست.

**•** HTTP Client و سیاست Error Handling / Interceptor

**•** Authentication Integration و Permission Handling در Frontend

**•** Testing Strategy و ابزارهای Unit / Component / E2E Test

|     | **قاعده نسخه‌بندی**<br><br>تا زمانی که تصمیمی در سند V1 تثبیت نشده است، توسعه‌دهنده یا AI نباید آن را به‌عنوان قرارداد قطعی معماری فرض کند. پس از تصمیم‌گیری درباره موارد فوق، سند Frontend Architecture V2 منتشر خواهد شد. |

**▌ ۱۴. چک‌لیست توسعه‌دهنده / AI**

**•** قبل از ایجاد فایل جدید مشخص کن کد متعلق به app، یک module یا shared است.

**•** اگر کد Domain را می‌شناسد، پیش‌فرض این است که داخل همان Module بماند.

**•** API را با Business Logic مخلوط نکن و Service را فقط برای منطق واقعی ایجاد کن؛ Service خالی یا نمایشی نساز.

**•** Page را سبک نگه دار و منطق قابل استفاده مجدد را به Component، Hook یا Service مناسب منتقل کن.

**•** Type و Schema را یک مفهوم فرض نکن و برای کامل‌بودن ظاهری معماری پوشه خالی نساز.

**•** در Refactorها مرز Public API ماژول‌ها را حفظ کن و وابستگی‌های متقاطع را افزایش نده.

**•** ظاهر و Styling باید با سند رسمی RWMS Frontend Visual Theme Contract هماهنگ باشد.

**▌ ۱۵. وضعیت سند**

**این سند قرارداد معماری V1 فرانت‌اند RWMS است. پس از انتخاب Router، State، Form، Validation، API Client، Authentication و Testing، نسخه V2 منتشر می‌شود.**
