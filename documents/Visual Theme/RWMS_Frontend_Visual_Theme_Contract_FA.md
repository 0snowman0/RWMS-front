این سند «قرارداد طراحی» پروژه است. تمرکز آن بر این است که چه حس و چه رفتار بصری باید در محصول نهایی رعایت شود؛ جزئیات پیاده‌سازی فنی Theme، کتابخانه UI یا ساختار کد در این سند تعیین نمی‌شود.

**اصل پایه** هر توسعه‌دهنده یا ابزار هوش مصنوعی که Frontend را توسعه می‌دهد باید خروجی خود را با قواعد این سند هماهنگ نگه دارد. افزودن رنگ یا الگوی بصری جدید خارج از این قرارداد، نیازمند تصمیم و مستندسازی جداگانه است.

**۱. هویت بصری مورد توافق**

رابط کاربری RWMS باید در نگاه اول حس «اعتماد، نظم، آرامش و کنترل» ایجاد کند. این سامانه قرار است حجم بالایی از فرم‌ها، جدول‌ها و اطلاعات عملیاتی را مدیریت کند؛ بنابراین زیبایی آن باید از نظم، فاصله‌گذاری مناسب، رنگ‌های کنترل‌شده و سلسله‌مراتب روشن اطلاعات به‌دست آید، نه از تزئینات زیاد.

**1\.** ظاهر سیستم حرفه‌ای و سازمانی باشد، اما خشک و سنگین به نظر نرسد.

**2\.** صفحات پیچیده باید در استفاده روزمره ساده و قابل فهم باقی بمانند.

**3\.** رنگ اصلی فقط برای هدایت توجه و اقدام‌های مهم استفاده شود؛ نه برای رنگ‌آمیزی گسترده صفحه.

**4\.** فضای سفید، سطوح روشن و Borderهای ملایم بخش اصلی حس آرام رابط هستند.

**5\.** در صفحات داده‌محور، خوانایی و تشخیص سریع وضعیت از زیبایی تزئینی مهم‌تر است.

**6\.** کل سیستم باید یک زبان بصری واحد داشته باشد؛ هر ماژول نباید ظاهر مستقل و سلیقه‌ای پیدا کند.

**۳. قرارداد استفاده از رنگ‌ها**

**۳.۱ Primary و Secondary**

**●** Primary (#155E75) برای مهم‌ترین اقدام هر ناحیه استفاده می‌شود؛ مانند «ثبت»، «تأیید» یا اقدام اصلی صفحه.

**●** در یک ناحیه کوچک، چند دکمه هم‌زمان نباید همگی Primary باشند. کاربر باید با یک نگاه اقدام اصلی را تشخیص دهد.

**●** Secondary (#0D9488) برای تأکید تکمیلی، کنترل‌های ثانویه، Badgeهای غیرهشداری یا عناصر راهنما استفاده می‌شود.

**●** استفاده وسیع از Primary یا Secondary به‌عنوان پس‌زمینه اصلی صفحه ممنوع است؛ این رنگ‌ها نقش هدایت و تأکید دارند.

**۳.۲ Background و Surface**

**●** پس‌زمینه عمومی صفحات #F8FAFC است تا سطح سفید کارت‌ها و فرم‌ها به‌آرامی از محیط جدا شود.

**●** کارت‌ها، Modalها، فرم‌ها، جدول‌ها و ناحیه‌های اصلی روی Surface سفید (#FFFFFF) قرار می‌گیرند.

**●** برای جداکردن بخش‌ها، اولویت با فاصله‌گذاری، Border ملایم و تغییر سطح بسیار خفیف است؛ نه سایه‌های سنگین.

**۳.۳ متن و Border**

**●** متن اصلی #1E293B است و برای تیترها، مقادیر مهم و محتوای اصلی استفاده می‌شود.

**●** متن توضیحی #475569 و متن کم‌اهمیت #64748B است. متن‌های ضروری نباید با رنگ بسیار کم‌رنگ نمایش داده شوند.

**●** Border استاندارد #E2E8F0 است. #CBD5E1 فقط در نقاطی که مرزبندی واضح‌تری لازم است استفاده می‌شود.

**۵. قرارداد ظاهر صفحات اصلی**

این بخش شکل دقیق پیاده‌سازی را تعیین نمی‌کند؛ فقط مشخص می‌کند کاربر در کل سامانه چه الگوی بصری ثابتی باید تجربه کند.

**۵.۱ Sidebar و ناوبری**

**●** Sidebar باید روشن، آرام و خوانا باشد. استفاده از Sidebar کاملاً مشکی یا بسیار تیره مبنای این Design System نیست.

**●** گزینه فعال باید با Primary یا Primary Soft قابل تشخیص باشد، بدون آنکه Contrast شدید و خسته‌کننده ایجاد کند.

**●** سطح‌های منو باید از نظر فاصله، آیکون و Typography قابل تفکیک باشند؛ نه با چند رنگ متفاوت.

**۵.۲ Header و Page Header**

**●** هر صفحه باید عنوان واضح، توضیح کوتاه در صورت نیاز و اقدام اصلی مشخص داشته باشد.

**●** Header نباید به ناحیه‌ای شلوغ برای دکمه‌ها تبدیل شود. عملیات کم‌کاربرد در منوی ثانویه یا ناحیه مناسب قرار می‌گیرند.

**۵.۳ جدول‌های داده**

**●** جدول‌ها باید خوانا و کم‌تنش باشند؛ Header مشخص، خطوط جداکننده ملایم و فضای کافی بین ردیف‌ها.

**●** رنگ‌آمیزی کامل ردیف‌ها فقط برای وضعیت‌های واقعاً مهم مجاز است. وضعیت عادی با Badge یا علامت کوچک نمایش داده می‌شود.

**●** عملیات ردیف باید منظم و قابل پیش‌بینی باشند. دکمه‌های متعدد رنگی در هر ردیف ممنوع است.

**۵.۴ فرم‌ها**

**●** فرم‌های طولانی باید به Sectionهای منطقی تقسیم شوند؛ کاربر نباید با یک صفحه متراکم از ورودی‌ها مواجه شود.

**●** Label، Help Text، Validation و Required State در تمام فرم‌ها رفتار یکسان داشته باشند.

**●** فیلدهای داینامیک تولیدشده توسط سیستم باید از نظر ظاهر دقیقاً با فیلدهای ثابت یکپارچه باشند؛ کاربر نباید حس کند دو سیستم متفاوت در یک فرم وجود دارد.

**۵.۵ Dashboard**

**●** Dashboard باید «اطلاعات مهم اکنون» را نشان دهد، نه تمام داده‌های موجود در سیستم.

**●** کارت‌ها محدود، معنادار و دارای سلسله‌مراتب باشند. استفاده از رنگ‌های متفاوت برای هر کارت مبنای طراحی نیست.

**قاعده تصمیم‌گیری** وقتی بین «نمایش اطلاعات بیشتر» و «حفظ وضوح صفحه» تعارض وجود دارد، اطلاعات ثانویه به سطح بعدی تعامل منتقل می‌شوند؛ صفحه اول هر ماژول باید قابل اسکن و آرام باقی بماند.

**۷. قرارداد توسعه برای انسان و AI**

هر شخص یا مدل هوش مصنوعی که صفحه یا کامپوننت جدیدی به RWMS اضافه می‌کند، قبل از تحویل باید این موارد را رعایت کند:

**●** از پالت رسمی همین سند استفاده شده باشد.

**●** اقدام اصلی صفحه با Primary قابل تشخیص باشد و اقدام‌های ثانویه با آن رقابت نکنند.

**●** Background، Surface، Text و Border با نقش‌های تعریف‌شده هماهنگ باشند.

**●** رنگ‌های Success / Warning / Danger / Info فقط برای معنی وضعیت استفاده شده باشند.

**●** صفحه در نگاه اول شلوغ و رنگارنگ نباشد و مسیر انجام کار برای کاربر روشن باشد.

**●** کامپوننت جدید از نظر اندازه، فاصله، Border، Radius و رفتار بصری با سایر اجزای سیستم یکپارچه باشد.

**●** اگر نیاز جدید با این قرارداد پوشش داده نمی‌شود، ابتدا قرارداد Design System توسعه داده شود و سپس صفحه جدید ساخته شود.

**نکته مهم** این سند قرارداد «خروجی و تجربه» است، نه قرارداد «روش پیاده‌سازی». انتخاب کتابخانه UI، روش مدیریت Theme یا ساختار داخلی کد می‌تواند در سند معماری Frontend تعریف شود، اما نتیجه نهایی باید با این قرارداد سازگار بماند.
